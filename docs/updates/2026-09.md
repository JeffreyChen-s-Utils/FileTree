## U-20260926-01 · 2026-09-26 · FileTree 0.1.0: scanner, treemap and PySide6 window · #release #scanner #treemap #gui #i18n

- **What**: new project. A disk-usage viewer in the spirit of TreeSize with a new, simpler window: pick a folder or drive (button, drive list, drag and drop, typed path, command line), watch live counts while it scans, then read a folder tree sorted largest first (with a share-of-parent bar), a squarified treemap coloured by file type, the 1,000 largest files (filterable) and the space per extension. Right-click to open, show in the file manager, copy the path, show in the treemap, scan that folder alone, or move to the Recycle Bin (confirmed first, numbers updated without a rescan). Export to CSV (UTF-8 with BOM for Excel) and JSON. English, Traditional Chinese (Taiwan) and Simplified Chinese, switchable at run time, Qt's own dialogs included; a built-in *How to use* guide.
- **Layers**: `file_tree/core` (standard library only: node, scanner, analysis, treemap layout, formatting, export) and `file_tree/gui` (PySide6). `test/test_layers.py` keeps Qt out of the core.
- **Numbers** (SSD, warm cache, this machine with 12 logical CPUs):
  - scanner threads, `C:\Program Files` (62,349 files, 6,219 folders): 1 → 1.27 s, 2 → 0.88 s, 4 → 0.67 s, 8 → 0.72 s; default set to 4. On a larger tree (653,652 files, 85,346 folders): 1 → 8.95 s, 2 → 6.61 s, 4 → 6.75 s, 8 → 7.27 s, 12 → 7.81 s. Cold cache, one thread: 28.5 s.
  - memory: about 185 MB for 739,000 entries (≈ 250 bytes each); only the root stores a full path and files share one empty children tuple.
  - analysis: two passes 1.40 s → one pass (`analysis.summarise`, `rfind` instead of `os.path.splitext`) 0.65 s for 653,824 files.
  - treemap layout: 0.08 s for 10,240 tiles at 1200×800.
- **Checks**: 89 tests pass, 1 skipped locally (creating a symlink needs developer mode on Windows; the Linux CI job runs it); `ruff check .` clean. CI: ruff, Windows with Python 3.10–3.14, Linux with Python 3.12; actions pinned to commit SHAs (`test/test_workflow_actions.py`); Dependabot on `dev` with a 7-day cooldown.
- **Files**: `file_tree/`, `test/`, `tools/make_screenshots.py`, `docs/images/main_window_*.png`, `README.md` and `README/README_zh-TW.md`, `README/README_zh-CN.md`, `architecture.md`, `CLAUDE.md`, `progress.md`.

## U-20260926-02 · 2026-09-26 · start_file_tree.py and a Nuitka build with Qt's translations · #release #build #nuitka #docs

- **What**: the owner asked for a root entry script and a guide to compiling with Nuitka. `start_file_tree.py` (repository root) starts the window like `python -m file_tree`; both now call `app.run()` (`test/test_start_script.py`). `tools/build_nuitka.py` compiles it: `python tools/build_nuitka.py` (program folder), `--onefile`, `--app` (macOS), any other option passed on to Nuitka. Guides in three languages: `nuitka.md`, `nuitka.zh-TW.md`, `nuitka.zh-CN.md`, linked from every README; the parity test now covers them too.
- **Why a script and not a bare command**: Nuitka 4.2.2's PySide6 plugin does not copy Qt's own translation catalogues, so a compiled FileTree showed Yes / No / Close in English in the Chinese interface. Inside the build Qt already looks in `PySide6/translations` (checked with a compiled probe: the path resolved there, the folder did not exist, `apply_qt_translation` returned False). `--include-package-data=PySide6:qtbase_zh_*.qm` copied nothing; `--include-data-files=<PySide6>/translations/qtbase_zh_TW.qm=PySide6/translations/qtbase_zh_TW.qm` (and zh_CN) worked: both catalogues loaded, "&Yes" became 是(&Y). The source path depends on where PySide6 is installed, so the script computes it from `qt_translation.CATALOGUES` (now public).
- **Output folders**: each form builds into `build/<mode>/`. With one shared `build/`, a one-file build staged its files in `start_file_tree.dist` and deleted it afterwards, silently removing a folder build made before it.
- **Numbers** (Windows 11, MSVC 14.5, Python 3.14.4, PySide6 6.11.2): folder build 75 MB, `FileTree.exe` inside; one-file build 22 MB (payload compressed to 29.6 %). A build with every core stalled the Discord bot running on this machine (gateway 13.3 s behind, `/sys churn` timed out), so the guides and `CLAUDE.md` recommend `--jobs=2`; the final check build ran with it and the bot logged no stall. That build (`build/standalone/start_file_tree.dist/FileTree.exe`) contains both catalogues and kept running for 6 s when started on the offscreen platform (smoke test only).
- **Not verified**: the macOS `--app` form and the Linux build (no such machine here); `progress.md` #4 covers macOS / Linux.
- **Files**: `start_file_tree.py`, `file_tree/__main__.py`, `file_tree/gui/qt_translation.py`, `tools/build_nuitka.py`, `test/test_build_nuitka.py`, `test/test_start_script.py`, `test/test_readme_parity.py`, `nuitka*.md`, `README.md`, `README/README_zh-*.md`, `architecture.md`, `CLAUDE.md`, `.gitignore`.

## U-20260926-03 · 2026-09-26 · The Nuitka script asks Qt where its translations are (Linux CI) · #incident #build #nuitka #ci

- **What happened**: the Linux CI job failed on `test/test_build_nuitka.py` right after U-20260926-02: `Qt translation catalogue missing: …/site-packages/PySide6/translations/qtbase_zh_TW.qm`. The PySide6 wheel keeps Qt's files under `PySide6/Qt/translations` on Linux, not `PySide6/translations` as on Windows, and the script had the Windows folder written into it (so did U-20260926-02's description of the option).
- **Fix**: `tools/build_nuitka.py` takes the source folder from `QLibraryInfo.path(TranslationsPath)` and copies the catalogues to the same place relative to the `PySide6` package inside the build; a test pins the Linux layout with a made-up folder. On Windows the generated options are unchanged from the verified build. The three `nuitka*.md` tables name both layouts.
- **Files**: `tools/build_nuitka.py`, `test/test_build_nuitka.py`, `nuitka.md`, `nuitka.zh-TW.md`, `nuitka.zh-CN.md`.

## U-20260926-04 · 2026-09-26 · The tree fills in while the scan runs; Stop keeps what was read · #done #scanner #gui

- **What**: `progress.md` #5 and #6 (the owner asked for TreeSize-style live display). The results page opens as soon as a scan starts, under a compact progress bar with Stop (`file_tree/gui/scan_bar.py`, replacing the full-page `scan_page.py`); the tree appears at once and fills in, biggest folders first. Stop now keeps the partial tree: `ScanCancelledError.partial` carries it, added up and sorted like a finished scan, with unread folders marked `NOT_SCANNED` (tooltip "Not scanned"), and the summary says "incomplete". The largest files and file types still arrive when the scan ends.
- **How**: the scanner adds each folder's files to the running totals of every folder above it as soon as the folder is listed (`_add_to_ancestors`, under the crawler's lock) and hands the root out first (`on_root` → `ScanWorker.started`). `FolderTreeModel` has a live mode: each folder's children are a sorted copy frozen until `refresh()`, which the window calls every 700 ms as a layout change that moves persistent indexes, so expanded folders, the selection and the scroll position survive and the view never sees a list change under it. Summary and status bar follow the progress signal.
- **Numbers**: running totals cost nothing measurable (A/B on the same 62,349-file tree, one process, alternating: 1.03/0.64/0.58 s with, 0.52/0.56/0.82 s without, with the machine at 91% CPU from other sessions). Live refresh on D:\Codes (739,000 entries, one subfolder expanded during the scan): 11–17 refreshes, mean 14–22 ms, worst 137–312 ms.
- **Also**: the treemap legend kept breaking inside a Chinese item; Qt ignores `<nobr>` and `white-space: nowrap` for CJK line breaks (measured with `QTextLayout`), so items now use no-break spaces and word joiners. README pictures regenerated.
- **Files**: `file_tree/core/scanner.py`, `file_tree/gui/{tree_model,scan_bar,scan_worker,results_view,main_window,strings}.py`, `test/test_scanner.py`, `test/test_gui.py`, `README.md`, `README/README_zh-*.md`, `architecture.md`, `docs/images/`.

## U-20260926-05 · 2026-09-26 · Ask for administrator rights at start, like TreeSize (Windows) · #done #gui #windows

- **What**: `progress.md` #14 (the owner asked for FileTree to ask for administrator rights so it can read everything). On Windows, before the window opens, FileTree starts a second copy of itself through the "runas" verb, which shows the UAC prompt; if that copy starts, this one exits, and a declined prompt simply continues without administrator rights. *View → Ask for administrator rights at start* turns the question off (setting `ask_admin_at_start`, on by default). *File → Restart as administrator* and a hint with the same button on the Problems tab (shown only when folders were denied and FileTree is not elevated) restart with the scanned folder as the argument. The title says "(Administrator)" when elevated.
- **How**: `file_tree/gui/elevation.py` — `IsUserAnAdmin`, `ShellExecuteW` with an explicit pointer-sized `restype` (an HINSTANCE; the default `c_int` truncates on 64-bit), and the restart command: a Nuitka build restarts `sys.argv[0]` (the file the user started, also for a one-file build), Python runs `-m file_tree` with `pythonw.exe` when it sits next to the interpreter, from the folder that holds the package. Nothing happens on macOS or Linux.
- **Checked**: scanning `C:\ProgramData` without rights lists 107 denied folders and shows the offer; the UAC prompt itself cannot be clicked in an automated run, so the start-up path is tested with the restart replaced (it returns 0 and opens no window when the elevated copy started). Also fixed in passing: the Problems table elides paths in the middle and gives the path column the space, and the status bar shows the final size of the selected entry when a scan ends (it kept the size from the moment it was selected during the scan).
- **Files**: `file_tree/gui/{elevation,app,main_window,results_view,strings}.py`, `test/test_elevation.py`, `README.md`, `README/README_zh-*.md`, `architecture.md`, `progress.md`.
- **Open items**: `progress.md` #15 (reasons shown in the system's language).

## U-20260926-08 · 2026-09-26 · Stop takes effect at once; live-scan tests no longer depend on timing · #incident #scanner #tests

- **What happened**: CI on Windows / Python 3.14 failed `test_stopping_keeps_what_was_read` once (run 36168469709): the scan finished before Stop took effect, so the result was complete instead of partial. Two causes. The test depended on sleeps (a slow runner reached Stop late). And the scanner itself noticed Stop only when its calling thread next woke up — up to one progress interval (0.1 s) — while the worker threads kept taking new folders.
- **Fix**: the worker threads now watch the cancel event and take no new folder once it is set; the calling thread stops waiting and raises `ScanCancelledError` after the workers finish the folders already in hand (`_Crawler._take`, `_Crawler.run`). The two live-scan GUI tests hold every folder but the root behind a gate the test opens, with one worker, so "still running when Stop arrives" is guaranteed instead of likely; six runs in a row pass.
- **Files**: `file_tree/core/scanner.py`, `test/test_gui.py`.

## U-20260926-10 · 2026-09-26 · Rescan one folder and swap it into the results · #done #scanner #gui

- **What**: `progress.md` #7. The context menu of a folder has **Rescan this folder**: only that branch is scanned again (progress in the scan bar, Stop keeps the old branch), then swapped into the tree while the rest of the results stay — the root row, every total above the folder, the Problems list (errors inside the old branch are replaced by the new ones), the treemap (kept where it was, or moved to the new branch if it showed the old one), and the status bar ("Rescanned photos: 250 B → 950 B"). The largest files and the per-type and per-age totals of the whole tree are then recomputed on a background thread (`AnalyseWorker`). Rescanning the root is the ordinary Rescan.
- **How**: `Node.replace_with` puts the new node in the old one's place under the old name and adds the differences up the chain; `FolderTreeModel.replace` does it inside a layout change and drops persistent indexes that pointed into the old branch (`_in_tree`), so the view never follows an index into a detached subtree — expanded folders and the selection elsewhere stay.
- **Files**: `file_tree/core/node.py`, `file_tree/gui/{tree_model,results_view,main_window,scan_worker,strings}.py`, `test/test_core.py`, `test/test_gui.py`, `README.md`, `README/README_zh-*.md`, `architecture.md`.
